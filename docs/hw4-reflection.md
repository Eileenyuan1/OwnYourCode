# HW4 Reflection

This is a joint reflection written by both team members. It covers the Claude Code setup, the test driven repo import rules, and the repo import page we built with Explore, Plan, Implement, Commit.

## How this workflow compares with how we used to work

Before this assignment, we moved from a plan straight into coding. In Cursor, planning and editing happened in the same flow, so it was easy to start changing files before the approach was settled. Claude Code makes the split explicit. Explore was only for reading, and in plan mode Claude could read the repo and propose a plan but could not edit anything until we approved it. We also stayed in manual mode instead of auto mode, so each file write waited for us to read the change and choose Yes. There were more confirmations than we were used to, but that kept us aligned, and the repo import page landed as three separate commits: the GitHub client ([d17de2a](https://github.com/Eileenyuan1/ownyourcode/commit/d17de2a)), importRepo ([3c057e6](https://github.com/Eileenyuan1/ownyourcode/commit/3c057e6)), and the /import page ([42f7b6e](https://github.com/Eileenyuan1/ownyourcode/commit/42f7b6e)). In class we were told to spend most of our time planning instead of jumping into implementation, and this workflow made that advice concrete.

The setup work followed the same pattern of starting rough and iterating. /init gave us a useful first CLAUDE.md, but it was mostly a summary of the PRD rather than instructions for working in this repo. We committed it unchanged ([33a4255](https://github.com/Eileenyuan1/ownyourcode/commit/33a4255)) and then improved it in two more commits, adding architecture decisions, coding conventions, a testing strategy, and project rules such as not committing unless asked ([3e73280](https://github.com/Eileenyuan1/ownyourcode/commit/3e73280), [70acbc2](https://github.com/Eileenyuan1/ownyourcode/commit/70acbc2)). Reviewing each version against the assignment requirements caught gaps that Claude did not flag on its own, such as the missing @import.

Test driven development changed our habits in a similar way. We used to ask the AI for a whole feature and test it afterwards. Writing failing tests first forced decisions the PRD had left open, such as whether a trailing slash is allowed or whether a file of exactly 100 KB is kept. Claude was helpful here when we asked it to list open questions before writing tests; for the size limits it raised eight, including one we had not considered, rejecting a repo with no files left. We wrote those decisions into PRD §5.1 before any code existed, so the tests became the spec and Claude only had to write the minimum code that passed. Every diff stayed small enough to review in a minute.

The workflow did not replace our own review, though. All 17 URL tests were green while github.com//repo was still accepted with an empty owner. We found it by reading the code and fixed it the same way, with a failing test ([cdb15c4](https://github.com/Eileenyuan1/ownyourcode/commit/cdb15c4)) and then a one line fix ([b5659c6](https://github.com/Eileenyuan1/ownyourcode/commit/b5659c6)). A bigger warning came from the permission setup: Claude invented a "bashCommands" format that Claude Code does not support and said the rules appeared to work ([86fa049](https://github.com/Eileenyuan1/ownyourcode/commit/86fa049)). We caught it only by checking the official docs and retesting in default mode, since auto mode can approve commands on its own ([4c9123b](https://github.com/Eileenyuan1/ownyourcode/commit/4c9123b)). Since then we treat "done" from Claude as a claim to check rather than a result.

Overall the workflow felt slower in the moment and faster across the whole assignment. We spent more time approving plans and reading tests, but almost nothing had to be rewritten, and the commit history explains itself.

## Which context practices helped

Plan mode was the most useful practice because it forced a pause between understanding the code and editing it. During the explore step Claude found that parseGitHubUrl, shouldIgnorePath, and filterRepoFiles already existed and listed what the page still needed, and that list became the plan. Saving the plan as docs/plans/repo-import-page.md ([e2292c2](https://github.com/Eileenyuan1/ownyourcode/commit/e2292c2)) was more reliable than leaving it in the chat, since a chat can be compacted or forgotten.

The same idea worked for setup and TDD. The first CLAUDE.md from /init pasted most of the PRD into itself, and replacing that with @docs/PRD.md and @AGENTS.md kept a single source of truth. Because every TDD decision was committed to the PRD, /clear was safe between tasks: a fresh session could rebuild its context from the repo instead of an old conversation. In the long TDD session, /compact with a focus on the import rules and commit style let Claude continue the same pattern without us repeating it.

CLAUDE.md also worked as memory across sessions. Rules we added once, such as not committing unless asked and not using dashes as punctuation, were followed in later sessions without reminders. They were not always followed in the same session that added them, so a rule only became reliable after a fresh start.

We also learned to manage sessions deliberately. claude --continue once opened a more recent session than the one we wanted, while claude --resume let us pick the right one and recover the /init log. Exporting each session right after finishing it, instead of at the end, kept the logs complete and made this reflection much easier to write.
